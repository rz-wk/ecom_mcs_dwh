# Процедуры (runbook)

## 1. Добавить проверку

1. Сформулировать проверяемое свойство одним предложением: например, «в `X` нет `Y`».
2. Выбрать механизм:
   - несколько систем или журнал загрузки — Python-гейт;
   - стандартное свойство колонки — generic-тест в `schema.yml`;
   - инвариант таблицы, грейн или бизнес-правило — singular-тест;
   - сверка двух слоёв — singular-тест `*_reconciliation`.
3. Проверить [матрицу покрытия](tests/README.md). Если владелец свойства уже есть, расширить его, а не создавать дубль.
4. Назвать тест по [naming.md](naming.md).
5. Добавить или обновить строку матрицы и карточку теста. Для Python-гейта обновить карточку соответствующего гейта.

### Пример

Свойство: в `mart_funnel` выручка ненулевая только на этапе `purchase`.

Механизм: 

- singular-тест, так как проверяется бизнес-инвариант набора строк витрины;
- Существующий `mart_funnel_metrics` проверяет неотрицательность `stage_count` и `revenue`, но не условие нулевой выручки для остальных этапов;
- Если это свойство не покрыто другим тестом, добавить отдельную проверку, например `mart_funnel_validity`, после проверки матрицы и текущей реализации;
- Добавить тест в матрицу и карточку `tests/singular/marts.md`.

## 2. Гейт упал

1. Открыть лог соответствующего Airflow-таска. Исключение содержит список проваленных проверок и доступные фактические значения. Например, `journal=2690751, fact=8072253`.
2. Расшифровать имя теста в карточке гейта:
   - [CSV -> ODS](tests/gates/csv_ods_check.md);
   - [ODS -> Core](tests/gates/integration_check.md).

### Аудит: журнал против факта ODS

Расхождение может указывать на дублирование или потерю строк после загрузки либо на внешнее изменение данных.

```sql
SELECT
    j.source_file,
    j.batch_date,
    j.rows_loaded,
    f.fact_rows
FROM ingestion.journal AS j
JOIN (
    SELECT
        _source_file,
        _batch_date,
        count(*) AS fact_rows
    FROM ods.events
    GROUP BY 1, 2
) AS f
    ON f._source_file = j.source_file
   AND f._batch_date = j.batch_date
WHERE j.status = 'loaded'
  AND j.rows_loaded <> f.fact_rows;
```

Запрос выявляет расхождения для пар source file / batch date, присутствующих в обеих таблицах. Если строка журнала или соответствующая группа ODS отсутствует полностью, это нужно диагностировать отдельно.

### Перезагрузка дня

Перезагрузить batch штатным идемпотентным путём:

```bash
python -m src.ingestion.load_ods \
    --batch-date <date> \
    --source-file data/raw/<yyyy-mm>.csv \
    --load-mode day
```

Типовые случаи:

- **Факт больше журнала**, особенно ровно в N раз — вероятно, дублирование строк;
- **Факт меньше журнала** — вероятная потеря строк после загрузки или внешнее вмешательство;
- **`rows_rejected` выше порога** — изучить файлы карантина в `staging`; менять `validation.max_rows_rejected` только после согласования.

После устранения причины очистить состояние упавшего гейта и нисходящих тасков через Airflow и повторить запуск.

## 3. Таск зелёный, но в OM пусто

Публикация в OM выполняется в режиме best-effort. Её сбой не обязательно влияет на статус загрузки.

Диагностика:

1. В логе таска найти предупреждения об OM, например:

   ```bash
   grep -E 'WARNING.*OM' <путь-к-логу>
   ```

2. Проверить типовые причины:
   - OM недоступен или токен истёк — `connection refused`, `401`;
   - после обновления OM изменился контракт API — `400 Invalid request format`; сверить payload в `dq.py` с актуальным описанием в [openmetadata.md](openmetadata.md);
   - таблица-носитель ещё не создана — кейс не привяжется; гейт `CSV -> ODS` должен идти после `emit_csv_lineage`;
   - тест не попадает в метрику Data Assets Coverage — это не обязательно ошибка публикации; проверить вкладку Data Quality на странице таблицы.

3. Не запускать `ingest_dbt_tests` отдельно до полного прогона `refresh_dbt_manifest -> process_dbt`. Иначе коннектор может прочитать устаревший `manifest` из общего `target/` и восстановить уже удалённые тесты.

## 4. Изменился контракт источника

Заголовок CSV является контрактом источника. Изменение состава или порядка колонок без обновления `_SOURCE_COLUMNS` в `load_ods` может привести к ошибке загрузки или позиционной подмене значений. Проверка `csv_header_matches_contract` предназначена для обнаружения такого изменения.

Порядок действий:

1. Проверить новый заголовок и определить, является ли изменение допустимым.
2. Обновить `_SOURCE_COLUMNS` и логику загрузки в `load_ods`.
3. Обновить CSV-сущность в OM. Эмиттер `emit_csv_lineage` должен синхронизировать её при штатном запуске.
4. Проверить гейт и обновить документацию, если изменились проверяемые свойства. Матрица меняется только при изменении состава проверок.

## 5. Ретроспективный аудит

Аудит — разовая операция, не встроенная в ежедневный конвейер: штатные гейты уже проверяют загружаемые batch.

1. Выполнить запрос из раздела 2 на нужном диапазоне дат.
2. Определить затронутые batch.
3. Перезагрузить затронутые дни штатным путём; для целого месяца использовать `--load-mode month`.
4. Повторно выполнить гейты и проверить результаты в Airflow и OM.
