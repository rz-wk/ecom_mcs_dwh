# Стандарт покрытия

Стандарт предназначен для проектирования проверок новых границ, таблиц и витрин. Он не ограничен текущей схемой `ecom_mcs_dwh`. Реализация для проекта приведена в [сводной матрице](tests/README.md).

## 1. Границы этапов

> Каждая граница между системами (`файл -> БД`, `БД -> БД`) должна иметь Python-гейт.

Для каждой границы необходимо рассмотреть шесть типов проверок:

| № | Тип | Контрольный вопрос | Dimension |
|---|---|---|---|
| 1 | Объём | Все ожидаемые строки дошли? | Consistency |
| 2 | Ключ | Ключ уникален после приёма? | Uniqueness |
| 3 | Время | Данные принадлежат своему batch? | Validity |
| 4 | Значения | Перечислимые поля не содержат неизвестных значений? | Validity |
| 5 | Диапазоны | Бизнес-величины находятся в допустимых пределах? | Validity |
| 6 | Метаданные | Batch-поля заполнены и согласованы? | Completeness |

Каждый пункт должен быть либо покрыт проверкой, либо осознанно исключён. Пропуск фиксируется в карточке гейта с обоснованием.

Источники эталонных значений:

- журнал загрузок — число принятых и отклонённых строк;
- контракт схемы — состав и порядок колонок;
- календарь batch — временные границы;
- конфигурация — пороги допустимых отклонений.

## 2. Таблицы хранилища

Для каждой таблицы следует ответить на пять вопросов:

| Контрольный вопрос | Dimension | Типовой тест |
|---|---|---|
| Грейн уникален? | Uniqueness | `unique` или `<model>_grain` |
| Ключевые поля заполнены? | Completeness | `not_null` |
| Перечислимые поля содержат допустимые значения? | Validity | `accepted_values` |
| Метрики находятся в бизнес-диапазоне? | Validity / Accuracy | `*_validity`, `*_metrics` |
| Временные поля согласованы (начало ≤ конец)? | Validity | `*_validity`, `*_valid_dates` |

Набор проверок зависит от назначения таблицы и её грейна. Необязательные поля не должны проверяться на `not_null` без бизнес-основания.

## 3. Витрины

> Каждая витрина должна иметь сверку с источником данных за сопоставимый период.

В дополнение к проверкам таблицы агрегаты витрины сверяются с исходным слоем за тот же период. Для этого используется singular-тест `*_reconciliation` с dimension Consistency.

**Пример**

Витрина продаж сверяет `purchase_count` и `revenue` с `fact_events` за соответствующий batch. Дополнительно проверяются заполненность ключевых полей, уникальность грейна и неотрицательность метрик.

Сверка должна учитывать семантику витрины: если между событием источника и записью витрины нет построчного соответствия, сравниваются сопоставимые агрегаты, а не количество строк разных грейнов.

## Пример масштабирования

При добавлении нового источника «возвраты»:

1. **Граница `CSV -> ODS`.** Создать гейт по образцу `csv_ods_check` и рассмотреть шесть типов проверок из п.1: контракт колонок, полнота загрузки по журналу, границы времени, допустимые типы возвратов, диапазоны сумм и заполненность batch-полей.
2. **Таблица возвратов в Core.** Проверить пять свойств таблицы из п. 2.
3. **Витрина возвратов.** Добавить сверку агрегатов с источником поверх проверок таблицы.
4. **Документация.** Именовать тесты по [naming.md](naming.md), добавить карточки и строки в [матрицу](tests/README.md).
