# Data Flow — поток данных

## 1. Назначение

Описывает путь события от исходного CSV до аналитических витрин: последовательность преобразований, изменение структуры данных и условия передачи между слоями.

Подробная реализация компонентов, оркестрация, проверки качества и публикация Lineage описаны в профильных разделах документации.

## 2. Сквозной поток данных

```text
Monthly CSV
    │
    ▼
Разбиение на дневные партии
    │
    ▼
PostgreSQL ODS
Исходные события + метаданные загрузки
    │
    ▼
PySpark Processing
Валидация -> карантин -> дедупликация
    │
    ▼
ClickHouse Core
Обработанные события с event_id
    │
    ▼
dbt
Измерения -> факты -> витрины
    │
    ▼
BI Apache Superset
```

Поток включает три вида преобразований:

- Подготовка и сохранение исходных данных: `CSV -> ODS`.
- Очистка и формирование канонического набора событий: `ODS -> Core`.
- Преобразование событий в аналитические сущности и показатели: `Core -> dbt-модели -> Marts`.

## 3. Этапы преобразования

### 3.1. Исходный `CSV -> ODS`

Источник содержит события e-commerce. Исходный файл организован по месяцам, загрузка в хранилище выполняется дневными партиями.

На этапе загрузки:

1. Проверяется соответствие заголовка CSV ожидаемому набору и порядку столбцов.
2. Данные разбиваются по дням и подготавливаются к загрузке.
3. Некорректные записи отделяются от принимаемых данных согласно правилам загрузчика.
4. Принятые строки загружаются в PostgreSQL.
5. Для партии сохраняются сведения о файле, дате, количестве загруженных и отклонённых строк, статусе и времени обработки.

Результат:
 
- события в ODS сохраняют исходную бизнес-структуру и дополняются техническими метаданными загрузки.

Контракт перехода: 

- заголовок источника должен соответствовать ожидаемой схеме; 
- партия должна иметь согласованные сведения о загрузке и временной диапазон.

Подробнее [ODS](ods.md)

### 3.2. `ODS -> Core`

PySpark читает дневную партию из ODS и подготавливает набор событий для аналитического хранения.

Основные преобразования:

1. Нормализация типов и значений.
2. Проверка обязательных атрибутов и бизнес-ограничений.
3. Отделение некорректных событий в карантин.
4. Удаление точных дубликатов по исходным полям события.
5. Формирование детерминированного `event_id`.
6. Загрузка результата в ClickHouse Core и сверка количества записей.

В Core данные имеют типы, соответствующие аналитическому хранению. Помимо атрибутов события, сохраняются технические поля, связывающие запись с исходной партией.

Результат: 

- обработанный набор событий, пригодный для построения аналитической модели.

Контракт перехода:

- Core должен соответствовать результату обработки партии; 
- идентификаторы событий должны быть уникальны, а временные атрибуты и распределение типов событий — согласованы с ODS с учётом предусмотренных преобразований.

Подробнее [Processing](processing.md), [Core](core.md).

### 3.3. `Core -> аналитическая модель dbt`

dbt преобразует события Core в сущности, соответствующие задачам аналитики.

Модель включает:

| Уровень | Объекты | Роль |
|---|---|---|
| Dimensions | `dim_user`, `dim_product`, `dim_category` | Контекст пользователей, товаров и категорий |
| Facts | `fact_sessions`, `fact_purchases` | Сессии и покупки как аналитические сущности |
| Marts | `mart_funnel`, `mart_sessions`, `mart_products`, `mart_users`, `mart_sales` | Данные для анализа воронки, сессий, поведения и продаж |

>На данном этапе меняется не только физическое представление, но и аналитическая гранулярность данных: отдельные события преобразуются в сущности и агрегаты, подходящие для конкретных вопросов бизнеса.

Зависимости между моделями определяются графом dbt. При построении итоговых витрин используются необходимые измерения и фактовые модели.

Результат: 
- набор аналитических таблиц, предназначенных для повторного использования в запросах и BI.

Подробнее [BI и аналитические модели](../bi/README.md).

### 3.4. `Витрины -> BI`

Apache Superset использует аналитические витрины для построения дашбордов и исследования показателей.

На этом этапе подготовленные данные представляются в визуальной форме. Бизнес-логика подготовки аналитических сущностей должна оставаться в слоях хранения и моделирования, и не дублироваться в отдельных визуализациях.

Результат:

- доступные для анализа показатели воронки, сессий, пользователей, товаров и продаж.

## 4. Контракты между слоями

| Переход | Что передаётся | Основной контракт |
|---|---|---|
| CSV -> ODS | Исходные события | Соответствие схемы источника, корректность загрузки и временного диапазона |
| ODS -> Core | Очищенные и дедуплицированные события | Согласованность количества и состава событий, корректность типов и временных атрибутов |
| Core -> dbt | Обработанные события | Соответствие схемам моделей и условиям аналитических преобразований |
| dbt -> витрины | Измерения и факты | Соблюдение гранулярности моделей и бизнес-инвариантов |
| Витрины -> BI | Аналитические таблицы | Соответствие структуры витрин запросам и визуализациям |

Проверки этих условий реализованы на соответствующих этапах и описаны в документации Data Quality. Таблица фиксирует логические контракты, не заменяет каталог конкретных тестов.

## 5. Гранулярность данных

В процессе обработки меняется гранулярность:

- Source / ODS: исходные данные событий.
- Core: отдельные обработанные события с техническим идентификатором.
- Dimensions: аналитические сущности пользователей, товаров и категорий.
- Facts: записи на уровне сессий и покупок в соответствии с правилами соответствующих моделей.
- Marts: данные на гранулярности, определяемой задачей каждой витрины — например, воронка, сессии, товары, пользователи или продажи.

Точная гранулярность каждой модели, ключи и правила расчёта определяются её SQL-реализацией и документированы в описании аналитической модели.

## 6. Границы ответственности

- Загрузка ODS отвечает за приём исходных данных и учёт партий.
- Processing отвечает за подготовку, фильтрацию некорректных записей и дедупликацию событий.
- Core хранит обработанные события для дальнейшей аналитической обработки.
- dbt отвечает за формирование аналитических сущностей и витрин.
- BI предоставляет интерфейс потребления аналитических данных.

Airflow управляет порядком выполнения этапов. Data Quality контролирует условия передачи данных между слоями, а Data Lineage фиксирует происхождение и зависимости. Подробности этих механизмов приведены в профильных разделах.
