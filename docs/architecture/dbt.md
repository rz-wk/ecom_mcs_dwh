# dbt — модели аналитического хранилища

## 1. Назначение и границы ответственности

Слой dbt отвечает за построение аналитических моделей в ClickHouse, выполняет SQL-трансформации между слоями Core и Marts хранилища `ecom_mcs_dwh`. На данном этапе событийные данные преобразуются в измерения, факты и агрегированные витрины для анализа пользовательского пути, выполняются тесты для контроль качества данных.

Ответственность dbt:

- построение dimensions и facts моделей;
- формирование аналитических витрин;
- инкрементальное обновление данных;
- проверка качества моделей dbt-тестами;
- формирование артефактов для публикации lineage и результатов тестирования.

Загрузка данных из ODS в Core, очистка и дедупликация событий выполняются вне dbt. Порядок запуска и передачу `batch_date` обеспечивает Airflow.

## 2. Организация проекта

Конфигурация проекта находится в `dbt_project.yml`. Модели распределены по двум схемам ClickHouse:

| Слой | Схема ClickHouse | Назначение |
|---|---|---|
| Core | `ecom_mcs_dwh_core` | Очищенные события, измерения и факты |
| Marts | `ecom_mcs_dwh_marts` | Агрегированные данные для аналитики |

Схемы задаются конфигурацией моделей. Макрос `custom_schema` переопределяет стандартное формирование имени схемы dbt: при наличии `+schema` используется указанное имя без добавления схемы профиля. Это позволяет направлять Core-модели и витрины в разные схемы ClickHouse.

### Основные компоненты

| Компонент | Назначение |
|---|---|
| `models/dimensions/` | Измерения пользователей, товаров и категорий |
| `models/facts/` | Факты покупок и сессий; источник событий Core |
| `models/marts/` | Аналитические витрины |
| `models/**/schema.yml` | Описание моделей и generic-тесты |
| `tests/` | Singular-тесты бизнес-инвариантов и сверок |
| `macros/incremental_filter.sql` | Общие правила фильтрации инкрементальных данных |
| `macros/custom_schema.sql` | Определение итоговой схемы модели |

Фактические параметры каждой модели — материализация, ключи сортировки и партиционирования, стратегия обновления — задаются в её SQL-конфигурации. Конкретная структура полей генерируемых таблиц приведена в [словаре данных](../data_model/data_dictionary.md).

## 3. Граф моделей

dbt модели разделяются на три группы:

- измерения;
- фактовые модели;
- аналитические витрины.

Граф показывает логические зависимости между моделями:

```text
ecom_mcs_dwh_core: fact_events
│
├── dim_user
├── dim_product ───────────────┐
├── dim_category ──────────────┤
│                              │
├── fact_purchases             │
│   ├── mart_sales             │
│   └── reconciliation tests   │
│                              │
├── fact_sessions              │
│   └── mart_sessions          │
│                              │
├── mart_funnel <──────────────┤
├── mart_products <────────────┘
└── mart_users
```

- `fact_events` — базовый источник событий для измерений, фактов и части витрин;
- `fact_purchases` — выделяет события покупок;
- `fact_sessions` — восстанавливает сессии по последовательности событий. 

Витрины агрегируют данные на собственной гранулярности.

Фактический порядок выполнения определяется графом dbt и оркестрацией Cosmos в Airflow.

## 4. Описание моделей

Для каждой модели ниже приведены назначение, grain данных, источники, алгоритм, правила обновления и ограничения. 

Полный перечень полей и типов у создаваемых таблиц см. в [словаре данных](../data_model/data_dictionary.md).

### 4.1. Измерения

Формируются из событий Core. Предоставляют общие атрибуты для аналитических моделей.

#### `dim_category`

**Назначение:** предоставить аналитическое представление категории товара, полученное из `category_code` событий.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_core` |
| Источник | `fact_events` |
| Grain | Одна строка на `category_id` |
| Материализация | `table` |
| Движок | `MergeTree()` |
| Ключ сортировки | `category_id ` |

**Алгоритм**

1. Для каждой категории выбирается последнее по `event_time` непустое значение `category_code` с помощью `argMaxIf`.
2. Строка `category_code` разбивается по точке на компоненты пути категории.
3. Формируются `category_path`, `category_root` и `category_leaf`.

**Особенности**

- Источник справочной информации — события, а не отдельный мастер-справочник категорий;
- Категория с пустым `category_code` не получает достоверного пути из этого источника;
- Модель перестраивается целиком при выполнении как `table`, не использует инкрементальный фильтр `batch_date`.

#### `dim_product`

**Назначение:** предоставить последние известные атрибуты товара для аналитических срезов.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_core` |
| Источник | `fact_events` |
| Grain | Одна строка на товар `product_id` |
| Материализация | `table` |
| Движок | `MergeTree()` |
| Ключ сортировки | `product_id ` |

**Алгоритм**

1. События группируются по `product_id`.
2. Для `category_id` и `brand` выбираются последние непустые значения по `event_time`.
3. Результат используется при обогащении товарных витрин.

**Особенности**

- `price` остаётся атрибутом события, поскольку может изменяться во времени, и не трактуется как постоянная характеристика товара;
- Модель отражает последние доступные атрибуты, а не историю их изменения;
- Перестроение модели выполняется целиком.

#### `dim_user`

**Назначение:** агрегировать временные границы активности пользователя.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_core` |
| Источник | `fact_events` |
| Grain | Одна строка на пользователя `user_id` |
| Материализация | `incremental` |
| Движок | `MergeTree()` |
| Ключ сортировки | `user_id ` |
| Инкрементальная стратегия | `delete+insert` |

Модель хранит:
- `first_seen` — минимальное время события пользователя;
- `last_seen` — максимальное время события пользователя.

Поведенческие агрегаты вынесены в `mart_users`.

**Алгоритм**

1. По `batch_date` определяются пользователи, у которых есть события в обрабатываемом батче;
2. Для этих пользователей выбирается полная история из `fact_events`;
3. Пересчитываются `first_seen` и `last_seen`;
4. Результат обновляется для затронутых пользователей.

**Особенности**

Пересчёт полной истории позволяет учитывать события прошлых дат, уже находящиеся в Core. Инкремент здесь определяется списком затронутых пользователей, а не только датой событий, записываемых в измерение.

### 4.2. Факты

#### `fact_purchases`

**Назначение:** выделить события покупок из общего потока событий.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_core` |
| Источник | `fact_events` |
| Grain | Одна строка на событие `purchase` |
| Материализация | `incremental` |
| Движок | `MergeTree()` |
| Партиционирование | `event_date` |
| Сортировка | `(event_date, event_id)` |
| Ключ | `event_id` |
| Инкрементальная стратегия | `delete+insert` |

**Алгоритм**

Из `fact_events` выбираются события типа `purchase`. Поля события сохраняются для последующих агрегаций, сверок и расчёта продаж.

**Инкрементальная обработка**

При переданном `batch_date` модель фильтрует события по `event_date`. При инкрементальном запуске без `batch_date` используется фильтр по значениям даты, превышающим максимальную дату целевой таблицы.

#### `fact_sessions`

**Назначение:** восстановить пользовательские сессии из последовательности событий.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_core` |
| Источник | `fact_events` |
| Grain | Одна строка на реконструированную сессию |
| Материализация | `incremental` |
| Движок | `MergeTree()` |
| Партиционирование | `toYYYYMM(session_start)` |
| Сортировка | `(user_id, session_start, session_id)` |
| Инкрементальная стратегия | `delete+insert` (pre_hook) |
| Граница новой сессии | Разрыв между соседними событиями более 30 минут |

**Алгоритм**

1. Определяются пользователи, активные в `batch_date`.
2. Из `fact_events` загружается полная история этих пользователей.
3. События упорядочиваются по `event_time`, затем по `event_id`.
4. `LAG` (оконная функция `lagInFrame`) позволяет определить время предыдущего события.
5. Новый `session_id` создаётся при первом событии пользователя либо при разрыве более 1800 секунд (строго больше 30 минут).
6. События агрегируются в сессии: рассчитываются начало и окончание сессии, число событий и производные временные метрики.
7. Предыдущие сессии затронутых пользователей удаляются синхронно, после чего записывается пересчитанный результат.

**Идентификатор и особенности**

`session_id` вычисляется как хеш `user_id` и `session_start` (`cityHash64(user_id, session_start)`). Исходное поле `user_session` не используется для определения границ сессий.

**Инкрементальная обработка** 

Для пользователей, имеющих события в текущем `batch_date`, модель синхронно удаляет прежние сессии и заново строит их по полной истории событий этих пользователей. Это дороже обработки только одного дня при большом количестве затронутых пользователей. Но позволяет корректно пересчитывать сессии при изменении истории на границе батча. 


### 4.3. Витрины

Все витрины материализуются как инкрементальные таблицы ClickHouse с движком `MergeTree()`. При переданном `batch_date` модели используют макрос `incremental_filter` и предварительное удаление соответствующих данных из целевой таблицы.

#### `mart_funnel`

**Назначение:** агрегировать события пользовательского пути по дням, категориям, брендам и этапам.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_marts` |
| Источники | `fact_events`, `dim_category` |
| Grain | День x категория x бренд x этап |
| Материализация | `incremental` |
| Движок | `MergeTree()` |
| Партиционирование | `toYYYYMM(event_date)` |
| Сортировка | `(event_date, category_id, brand, funnel_stage)` |
| Инкрементальная стратегия | `delete+insert` (pre_hook) |

**Алгоритм**

- Учитываются события `view`, `cart`, `remove_from_cart` и `purchase`.
- Данные агрегируются по `event_date`, `category_id`, `brand` и этапу.
- Этап становится значением `funnel_stage`, а количество событий записывается в `stage_count`.
- Рассчитываются число событий этапа и выручка. Выручка рассчитывается только для событий `purchase`, для остальных этапов сумма равна нулю.
- Атрибуты категории присоединяются из `dim_category`.

`NULL` в `category_id` заменяется на `0`, а `NULL` в `brand` — на пустую строку. Эти значения служат техническими категориями группировки и не являются реальными атрибутами товара.

**Обновление**

Перед пересчётом удаляются данные целевой даты, затем витрина строится для `batch_date`. Такой порядок делает повторный запуск даты воспроизводимым на уровне этой модели.

#### `mart_sales`

**Назначение:** агрегировать покупки и выручку по дням, категориям и брендам.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_marts` |
| Источники | `fact_purchases`, `dim_category` |
| Grain | Дата покупки x категория x бренд |
| Материализация | `incremental` |
| Движок | `MergeTree()` |
| Партиционирование | `toYYYYMM(purchase_date)` |
| Сортировка | `(purchase_date, category_id, brand)` |
| Инкрементальная стратегия | `delete+insert` (pre_hook) |


**Метрики**

- количество событий покупки;
- число уникальных покупателей;
- число уникальных товаров;
- выручка;
- средняя цена покупки.

Покупатели и товары считаются через `uniqExact(user_id)` и `uniqExact(product_id)`, выручка — через сумму цены `sum(price)`, средняя цена — через среднее значение цены `avg(price)`. Категория и бренд используются для сегментации.

**Обновление**

Перед пересчётом удаляются строки за `purchase_date`. В источнике `fact_purchases` дата называется `event_date`, а в запросе витрины она переименовывается в `purchase_date`.

#### `mart_products`

**Назначение:** предоставить дневные показатели событий и покупок в разрезе товара.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_marts` |
| Источники | `fact_events`, `dim_product`, `dim_category` |
| Grain | День x товар |
| Материализация | `incremental` |
| Движок | `MergeTree()` |
| Партиционирование | `toYYYYMM(event_date)` |
| Сортировка | `(event_date, product_id)` |
| Инкрементальная стратегия | `delete+insert` (pre_hook) |
 

**Алгоритм**

События группируются по `event_date` и `product_id`. Рассчитываются количества событий по типам и показатели выручки. Атрибуты товара и категории присоединяются из измерений: категория и бренд подтягиваются из `dim_product`, названия уровней категории из `dim_category`.

**Обновление**

Для `batch_date` удаляются старые строки соответствующей даты, затем агрегаты пересчитываются из `fact_events`. Повторная обработка даты не должна добавлять повторный набор агрегатов.

#### `mart_sessions`

**Назначение:** агрегировать показатели пользовательских сессий для аналитики поведения.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_marts` |
| Источник | `fact_sessions` |
| Grain | Одна строка на сессию |
| Материализация | `incremental` |
| Движок | `MergeTree()` |
| Партиционирование | `toYYYYMM(session_start)` |
| Сортировка | `(session_start, user_id, session_id)` |
| Инкрементальная стратегия | `delete+insert` (pre_hook) |

Модель переносит сессионные показатели из `fact_sessions` в витрину без дополнительной агрегации.

**Инкрементальная обработка**

Целевые записи удаляются по условию `session_end` не раньше начала `batch_date` минус 30 минут. Источник фильтруется макросом по тому же временному порогу. Такой подход учитывает сессии, затронутые границей партии.

В текущем макросе для такого режима задана нижняя граница без верхней границы. Поэтому при наличии в источнике будущих относительно `batch_date` сессий они также могут попасть в выборку. Корректность зависит от хронологического режима обработки и отсутствия будущих данных в источнике; при поддержке произвольных бэкфиллов это условие необходимо пересмотреть.

#### `mart_users`

**Назначение:** агрегировать дневную активность пользователей.

| Параметр | Значение |
|---|---|
| Схема | `ecom_mcs_dwh_marts` |
| Источник | `fact_events` |
| Grain | День x пользователь |
| Материализация | `incremental` |
| Движок | `MergeTree()` |
| Партиционирование | `toYYYYMM(event_date)` |
| Сортировка | `(event_date, user_id)` |
| Инкрементальная стратегия | `delete+insert` (pre_hook) |

Модель агрегирует `fact_events` по дате и пользователю. Для каждого пользователя за день рассчитываются общее число событий, просмотры, добавления и удаления из корзины, покупки и выручка, количество различных значений исходного `user_session` через `uniqExact`.

`source_session_count` — число уникальных идентификаторов `user_session` в событиях источника. Это не то же самое, что число восстановленных сессий в `fact_sessions`: правила определения сессий различаются.

**Обновление**

Строки за `batch_date` удаляются и пересчитываются по событиям этой даты.

## 5. Инкрементальная обработка

Общий макрос `incremental_filter(date_col, lookback_col, lookback_minutes)` поддерживает три режима:

| Условия | Поведение |
|---|---|
| Инкрементальная модель и задан `batch_date`, без lookback | Равенство даты источника `batch_date`. Фильтрация по указанной дате |
| Инкрементальная модель и заданы `batch_date`, с `lookback_col` | Фильтрация по времени от `batch_date 00:00:00` минус `lookback_minutes` |
| Инкрементальная модель без `batch_date` | Фильтрация по значениям `date_col`, превышающим максимум в целевой таблице |
| Полная сборка с заданным `batch_date` | Фильтрация по указанной дате, если это предусмотрено вызовом макроса |

Макрос отвечает за фильтрацию исходного набора, а не за удаление устаревших строк из целевой таблицы. Для моделей с дневным пересчётом удаление реализовано через `pre_hook`.

Для витрин с предварительным удалением батча по дате используется последовательность «удаление целевого среза -> построение нового среза». Для `dim_user` и `fact_sessions` инкрементальная логика основана на пересчёте всех данных затронутых пользователей.

## 6. Тестирование моделей

В dbt используются два вида тестов:

- **generic-тесты** в `schema.yml`: проверка свойств колонок, например `not_null`, `unique`, `accepted_values`;
- **singular-тесты** в SQL-файлах `tests/`: проверка бизнес-инвариантов, гранулярности таблиц, корректности метрик и сверок между слоями.

Полная матрица проверок, владелец каждого свойства и порядок диагностики описаны в [документации контроля качества](../data_quality/README.md). Подробности интеграции результатов в OpenMetadata — в [разделе OpenMetadata](../data_quality/openmetadata.md).

## 7. Airflow и OpenMetadata

Airflow запускает dbt через Cosmos `DbtTaskGroup`, передаёт `batch_date` и формирует отдельные каталоги артефактов. Сначала выполняются модели, затем тесты в соответствии с настройкой `TestBehavior.AFTER_ALL`.

После завершения dbt Airflow:

1. публикует lineage dbt-моделей;
2. запускает ingestion-коннекторы OpenMetadata для Core и Marts;
3. отдельно публикует результаты reconciliation-тестов, которые стандартный коннектор не может связать с одной таблицей.

Airflow отвечает за порядок запуска, а OpenMetadata — за представление lineage и результатов качества. 

Подробности в [документации Airflow](airflow.md) и [документации OpenMetadata](../data_quality/openmetadata.md).

## 8. Ограничения

| Область | Ограничение |
|---|---|
| `fact_sessions` | Пересчитывается полная история затронутых пользователей; стоимость зависит от объёма их истории |
| `dim_category`, `dim_product` | Отражают последние известные атрибуты, а не исторические версии измерений |
| Инкрементальные модели | Повторяемость обеспечивается логикой отдельных моделей, а не общей транзакцией между всеми слоями |
| OpenMetadata | Результаты dbt-тестов публикуются после выполнения группы dbt; сбой публикации не откатывает трансформации |
