# ODS — Operational Data Store

## 1. Назначение

ODS — слой первичного хранения данных событий в PostgreSQL. Загружает данные из исходных CSV-файлов, сохраняет их в реляционной структуре и обеспечивает контролируемую передачу дневных батчей на обработку в PySpark.

На данном этапе не выполняются аналитические преобразования: построение пользовательских сессий, расчёт бизнес-показателей или агрегация событий в аналитические витрины.

## 2. Состав слоя

| Таблица | Назначение |
|---|---|
| `ods.events` | Хранение загруженных событий |
| `ingestion.journal` | Журнал результатов загрузки по исходному файлу и дате батча |

- `ods.events` хранит данные события и технические метаданные происхождения; 
- `ingestion.journal` фиксирует статус обработки батча, количество загруженных и отклонённых строк, время выполнения и сведения об ошибке.

## 3. Таблица `ods.events`

### Структура

| Поле | Тип PostgreSQL | Обязательность | Назначение |
|---|---|---|---|
| `event_time` | `TIMESTAMPTZ` | NOT NULL | Время события |
| `event_type` | `VARCHAR(16)` | NOT NULL | Тип события |
| `product_id` | `BIGINT` | NOT NULL | Идентификатор товара |
| `category_id` | `BIGINT` | NOT NULL | Идентификатор категории |
| `category_code` | `TEXT` | NULL | Код категории |
| `brand` | `TEXT` | NULL | Бренд товара |
| `price` | `NUMERIC(12,2)` | NOT NULL | Цена события |
| `user_id` | `BIGINT` | NOT NULL | Идентификатор пользователя |
| `user_session` | `UUID` | NULL | Идентификатор сессии источника |
| `_ingested_at` | `TIMESTAMPTZ` | NOT NULL | Время загрузки записи, по умолчанию `now()` |
| `_source_file` | `TEXT` | NOT NULL | Имя исходного файла |
| `_batch_date` | `DATE` | NOT NULL | Дата обрабатываемого батча |

- Пол] 1-9 соответствуют бизнес-атрибутам исходного события;
- Поля с префиксом `_` добавлены для учёта загрузки и связи записи с исходной партией.

### Организация хранения

Таблица секционирована по диапазонам `event_time`:

```sql
PARTITION BY RANGE (event_time)
```

Для доступа к данным предусмотрены индексы:

- `(_source_file, _batch_date, event_time)` — поиск записей по исходному файлу и батчу с учётом времени события;
- `(event_time)` — фильтрация по времени;
- `(user_id)` — выборка событий пользователя.

Первичный ключ или ограничение уникальности для событий в DDL не определены. Устранение дубликатов выполняется на следующем этапе обработки.

## 4. Таблица `ingestion.journal`

### Структура

| Поле | Тип PostgreSQL | Назначение |
|---|---|---|
| `source_file` | `TEXT` | Имя исходного файла |
| `batch_date` | `DATE` | Дата батча |
| `status` | `TEXT` | Статус загрузки |
| `rows_loaded` | `BIGINT` | Количество загруженных строк |
| `rows_rejected` | `BIGINT` | Количество отклонённых строк |
| `started_at` | `TIMESTAMPTZ` | Время начала обработки |
| `finished_at` | `TIMESTAMPTZ` | Время завершения |
| `error` | `TEXT` | Сведения об ошибке |

Составной первичный ключ `(source_file, batch_date)` определяет уникальную запись журнала для пары «исходный файл — дата батча».

Журнал используется для контроля состояния загрузки и сверки количества записей между этапами. В частности, проверка `CSV -> ODS` сопоставляет число строк в `ods.events` с `rows_loaded` в журнале.

Допустимые значения `status` и правила переходов между статусами определяются реализацией загрузчика.

## 5. Контракт входных данных

Загрузчик ожидает фиксированный набор исходных столбцов в установленном порядке:

- `event_time`
- `event_type`
- `product_id`
- `category_id`
- `category_code`
- `brand`
- `price`
- `user_id`
- `user_session`

Несовпадение заголовка с ожидаемым контрактом является основанием для отклонения источника. Некорректные строки могут быть отделены в карантин на этапе загрузки.

В `ODS` сохраняется исходная структура событий с приведением типов к схеме `PostgreSQL`. Семантическая очистка, дедупликация и формирование `event_id` относятся к этапу `Processing`, а не к `ODS`.

## 6. Передача данных в `Processing`

Следующий этап читает данные `ODS` дневными партиями и обрабатывает их в `PySpark`.

Для идентификации батча используются технические атрибуты `_source_file` и `_batch_date`. Они также позволяют связать записи ODS с результатом обработки и выполнять сверки между слоями.

Успешный статус загрузки сам по себе не гарантирует бизнес-корректность всех записей. Передача батча сопровождается отдельной проверкой `CSV -> ODS`, которая контролирует журнал, количество строк, допустимое число отклонений и временные границы.

Подробности проверки описаны в [Data Quality](../data_quality/README.md).

## 7. Ограничения и эксплуатационные особенности

- Секционирование по времени события. Для вставки записей должна существовать подходящая секция. Управление секциями — часть инфраструктуры загрузки;
- Нет уникальности на уровне события. ODS допускает наличие дубликатов, устранение которых выполняется в Processing;
- Nullable-поля. `category_code`, `brand` и `user_session` допускают `NULL` по схеме ODS. Дополнительные требования к качеству проверяются на соответствующих этапах;
- Два временных атрибута. `event_time` описывает время события, `_ingested_at` — время загрузки. Они решают разные задачи и не должны взаимозаменяться;
- Журнал не заменяет проверку данных. Статус и счётчики загрузки необходимо сверять с фактически сохранёнными строками.
