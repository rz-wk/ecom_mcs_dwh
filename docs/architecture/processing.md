# Processing — обработка событий в PySpark

## 1. Назначение

Processing — слой преобразования данных между PostgreSQL ODS и ClickHouse Core. Он подготавливает исходные события к аналитическому хранению: нормализует данные, отбрасывает некорректные записи в карантин, удаляет точные дубликаты и формирует технический идентификатор события.

Основная задача этапа — обеспечить согласованный набор событий для последующего построения аналитических моделей.

## 2. Входные и выходные данные

| Параметр | Описание |
|---|---|
| Источник | `ods.events` в PostgreSQL |
| Единица обработки | Дневной батч |
| Выходной слой | `ecom_mcs_dwh_core.fact_events` в ClickHouse |
| Карантин | Parquet-файлы с некорректными событиями |
| Основной идентификатор | `event_id`, детерминированно вычисляемый из полей события |

- Входная запись содержит девять бизнес-полей исходного события и технические метаданные загрузки. 
- Выходная запись дополнительно содержит `event_id` и производный атрибут `event_date`.

## 3. Последовательность обработки

### 3.1. Чтение батча

PySpark получает из ODS события, относящиеся к обрабатываемой дате. Технические атрибуты `_source_file`, `_batch_date` и `_ingested_at` сохраняются для трассировки происхождения данных.

### 3.2. Нормализация и валидация

Данные приводятся к типам, необходимым для записи в ClickHouse. Проверяются допустимость события и обязательные атрибуты.

В частности, правила обработки учитывают:

- допустимые типы событий: `view`, `cart`, `remove_from_cart`, `purchase`;
- наличие обязательных значений;
- отсутствие отрицательной цены;
- наличие `user_session` согласно правилам текущей реализации.

Записи, не прошедшие проверку, отделяются от основного потока в карантин.

### 3.3. Карантин

Некорректные события сохраняются в Parquet для последующего анализа. Они не должны попадать в основной набор `fact_events`.

Карантин позволяет отделить обработку валидных данных от исследования проблем источника, не смешивая некорректные записи с аналитическим слоем.

### 3.4. Дедупликация

Из валидных событий удаляются точные дубликаты по исходным бизнес-полям события. При сохранении одной записи используется наиболее раннее значение `_ingested_at`.

Дедупликация выполняется до загрузки в Core. Она не является поиском всех возможных бизнес-дубликатов: события, различающиеся хотя бы одним полем сравнения, могут сохраниться как отдельные записи.

### 3.5. Формирование идентификатора

Для обработанного события вычисляется детерминированный `event_id` на основе хеша полей события.

Идентификатор используется для идентификации записи в Core и проверок уникальности. Он не является исходным идентификатором события из источника.

### 3.6. Загрузка в Core

Подготовленный набор записывается в `ecom_mcs_dwh_core.fact_events`. Перед загрузкой текущей партии существующие данные этой партии удаляются, после чего вставляется новый результат. После записи выполняются проверки количества и согласованности данных.

## 4. Преобразование структуры

| Атрибут | ODS | Core | Преобразование |
|---|---|---|---|
| `event_time` | `TIMESTAMPTZ` | `DateTime64(3, 'UTC')` | Приведение к типу ClickHouse |
| `event_type` | `VARCHAR(16)` | `LowCardinality(String)` | Тип для хранения категориальных значений |
| `product_id` | `BIGINT` | `UInt32` | Приведение к целочисленному типу |
| `category_id` | `BIGINT` | `UInt64` | Приведение к целочисленному типу |
| `category_code` | `TEXT` | `LowCardinality(Nullable(String))` | Сохранение nullable-значения |
| `brand` | `TEXT` | `LowCardinality(Nullable(String))` | Сохранение nullable-значения |
| `price` | `NUMERIC(12,2)` | `Decimal(12,2)` | Сохранение точности цены |
| `user_id` | `BIGINT` | `UInt32` | Приведение к целочисленному типу |
| `user_session` | `UUID` | `Nullable(UUID)` | Сохранение идентификатора сессии |
| — | — | `event_id UInt64` | Вычисляемый идентификатор |
| — | `event_time` | `event_date Date` | Производная календарная дата |
| `_source_file` | `TEXT` | `LowCardinality(String)` | Сохранение происхождения |
| `_batch_date` | `DATE` | `DATE` | Сохранение даты партии |
| `_ingested_at` | `TIMESTAMPTZ` | `DateTime64(3, 'UTC')` | Сохранение времени загрузки |

Примечание:

- преобразование `product_id` и `user_id` в `UInt32` сужает допустимый диапазон значений относительно PostgreSQL `BIGINT`.

## 5. Контракт `Processing -> Core`

Передача партии в Core предполагает выполнение следующих условий:

- некорректные события отделены от основного набора;
- точные дубликаты удалены по правилам реализации;
- `event_id` сформирован для каждой выходной записи;
- временные атрибуты соответствуют обрабатываемой партии;
- количество и распределение событий согласованы с результатом обработки.

После загрузки отдельная интеграционная проверка контролирует количество записей, уникальность `event_id`, диапазон времени, типы событий и другие инварианты.

Подробности проверок [Data Quality](../data_quality/README.md)

## 6. Идемпотентность и повторная обработка

Перед вставкой результата текущей партии существующие записи этой партии удаляются. Это позволяет повторно сформировать результат вместо простого добавления нового набора к старому.

При этом удаление и вставка не образуют единую атомарную операцию. При сбое между ними Core может временно остаться без данных соответствующей партии. Поэтому повторный запуск и последующая проверка согласованности имеют эксплуатационное значение.

## 7. Ограничения

- Дедупликация ограничена точными совпадениями. События, различающиеся атрибутами, не считаются дублями автоматически.
- Хеш не гарантирует абсолютную уникальность. Теоретически возможны коллизии `event_id`.
- Сужение типов идентификаторов. Значения вне диапазона `UInt32` нельзя безопасно записать без дополнительной обработки.
- Карантин требует отдельного управления. Сохранение некорректных записей само по себе не обеспечивает их исправление или повторную загрузку.
- Перезапись партии не атомарна. Необходимо учитывать состояние Core при сбоях во время загрузки.
