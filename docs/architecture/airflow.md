# Airflow — оркестрация конвейера

## 1. Назначение

Apache Airflow управляет ежедневным конвейером `ecom_mcs_dwh`: загрузкой исходных данных, обработкой ODS → Core, проверками качества, трансформациями dbt и публикацией lineage и результатов тестирования в OpenMetadata.

Airflow отвечает за расписание, порядок выполнения, передачу параметров, повторы и статус задач. Бизнес-логика находится в загрузчике ODS, PySpark-модуле, SQL-моделях dbt и проверках качества.

## 2. Конфигурация DAG

Файл DAG: `airflow/dags/ecom_mcs_dwh_daily_pipeline.py`.

Параметры читаются из конфигурации проекта `_conf`. Она определяет:

- `dag_id`, `start_date` и часовой пояс;
- расписание, `catchup` и `max_active_runs`;
- таймаут выполнения DAG `dagrun_timeout`;
- число повторов `retries` и задержку между попытками `retry_delay_minutes`;
- пути к Python, Airflow Python и dbt;
- параметры запуска вспомогательных процессов и подключения к внешним системам.

В качестве даты батча используется логическая дата Airflow `ds` в формате `YYYY-MM-DD`. Для CSV выбирается файл соответствующего месяца: `data/raw/YYYY-MM.csv`.

## 3. Граф выполнения

Активная последовательность выполнения:

```text
process_csv_ods
    ↓
emit_csv_lineage
    ↓
test_csv_ods
    ↓
process_ods_core
    ↓
emit_spark_lineage
    ↓
test_ods_core
    ↓
refresh_dbt_manifest
    ↓
process_dbt (Cosmos TaskGroup)
    ↓
emit_dbt_lineage
    ↓
ingest_dbt_tests
    ↓
push_dbt_test_results
```

Зависимости между задачами задаются оператором `>>`. При стандартном правиле выполнения `all_success` downstream-задача не запускается, если upstream-задача завершилась ошибкой.

Lineage-эмиттеры для CSV и Spark выполняются до соответствующих DQ-гейтов. Поэтому наличие lineage-события в OpenMetadata не означает, что проверка качества пройдена.

## 4. `CSV -> ODS`

### `process_csv_ods`

Запускает загрузчик `src.ingestion.load_ods` для текущего батча (`ds`) и соответствующего месячного CSV-файла (`data/raw/YYYY-MM.csv`):

```bash
python -m src.ingestion.load_ods \
  --batch-date "{ds}" \
  --source-file "data/raw/{ds[:7]}.csv" \
  --load-mode config \
  --resume
```

Параметры:

- `--batch-date` — дата обрабатываемого батча;
- `--source-file` — CSV-файл месяца, содержащего дату батча;
- `--load-mode config` — режим загрузки: один день или весь месяц одним проходом (day, month), выбирается загрузчиком из конфигурации проекта, по умолчанию day;
- `--resume` — при сбое продолжать с места остановки без перезаливки корректно загруженных, по умолчанию включен.

Загрузчик реализует чтение исходного CSV, загрузку в PostgreSQL ODS и логику возобновления. Airflow передаёт параметры, но не выполняет загрузку самостоятельно.

При историческом бэкфилле предусмотрена обработка данных в месячном режиме. Это отдельный сценарий запуска загрузчика; его не следует смешивать с режимом, который использует ежедневный DAG.

Примеры итоговых команд:

```bash
# Дневной прогон
python -m src.ingestion.load_ods \
  --batch-date 2019-10-01 \
  --source-file data/raw/2019-10.csv
  --resume
```

```bash
# Месячный прогон (полный бэкфилл)
python -m src.ingestion.load_ods \
  --batch-date 2019-10-01 \
  --source-file data/raw/2019-10.csv \
  --load-mode month
  --resume
```

### `emit_csv_lineage`

Запускает lineage эмиттер `src.lineage.emit_csv` для исходного файла. Эмиттер публикует сведения об источнике через OpenLineage, чтобы CSV-сущность была доступна в каталоге метаданных. Таск выполняется после загрузки ODS и до проверки качества этого этапа.

### `test_csv_ods`

Запускает:

```bash
python -m src.validation.csv_ods_check \
  --batch-date "{ds}" \
  --source-file "data/raw/{ds[:7]}.csv"
```

Гейт проверяет границу `CSV -> ODS`. При неуспешной проверке задача завершается с ошибкой и блокирует последующие задачи активной цепочки.

Состав проверок и порядок диагностики см. [гейт `CSV -> ODS`](../data_quality/tests/gates/csv_ods_check.md).

## 5. `ODS -> Core`

### `process_ods_core`

Запускает `src.pyspark.deduplicate_events` для текущего батча:

```bash
python -m src.pyspark.deduplicate_events \
  --batch-date "{ds}" \
  --source-file "{ds[:7]}.csv"
```

Для запуска Spark задаются переменные окружения `PYSPARK_PYTHON` и `PYSPARK_DRIVER_PYTHON`. Путь к интерпретатору определяется конфигурацией окружения.

PySpark-модуль отвечает за обработку событий, дедупликацию и загрузку результата в ClickHouse Core. Детали преобразования и технические правила описаны в [Processing](processing.md) и [Core](core.md).

### `emit_spark_lineage`

Запускает эмиттер `src.lineage.emit_spark` для публикации lineage обработки `ODS -> Core`.

### `test_ods_core`

Запускает:

```bash
python -m src.validation.integration_check \
  --batch-date "{ds}" \
  --source-file "{ds[:7]}.csv"
```

Гейт проверяет согласованность данных между ODS и Core. Если проверка завершается ошибкой, дальнейшая цепочка не выполняется.

Состав проверок: [гейт `ODS -> Core`](../data_quality/tests/gates/integration_check.md).


## 6. Core -> Marts: dbt

### `refresh_dbt_manifest`

Перед запуском dbt-группы выполняет `dbt parse` в каталоге dbt-проекта. Это обновляет артефакты проекта, которые затем используют dbt и lineage-эмиттеры.

Для задачи в dag явно отключены повторы, установлено `retries=0`.

### `process_dbt`

`process_dbt` — группа задач `DbtTaskGroup`, сформированная с помощью Cosmos. 

Основные параметры:

| Параметр | Настройка |
|---|---|
| Проект | `dbt_project.yml` |
| Профиль | `ecom_mcs_dwh` |
| Target | `local` |
| Переменная батча | `batch_date = "{{ ds }}"` |
| Режим построения графа | `LoadMode.DBT_MANIFEST` |
| Выполнение тестов | `TestBehavior.AFTER_ALL` |
| Исполнитель | `ExecutionMode.SUBPROCESS` |
| Путь к dbt | `_DBT_EXEC_PATH` из конфигурации |
| Каталог артефактов | Изолированный `target-path` для задачи |
| Повторы | `retries=0` |

`ProjectConfig` задаёт путь к dbt-проекту и manifest. `ProfileConfig` использует профиль `ecom_mcs_dwh`, target `local` и `profiles.yml`. `RenderConfig` загружает граф из manifest. `ExecutionConfig` задаёт внешний исполняемый файл dbt и запуск в отдельном процессе.

Для `process_dbt` используется отдельный каталог артефактов в `target/<task_id>/`. Это изолирует файлы запуска и снижает риск конфликтов чтения и записи при работе с manifest и результатами dbt.

При `TestBehavior.AFTER_ALL` тесты выполняются единым блоком после построения моделей группы, а не после каждой модели. Неуспешные dbt-тесты могут привести к ошибке группы и остановить последующую цепочку.

Описание моделей, зависимостей, materialization и инкрементальной логик в [dbt](dbt.md).

## 7. Публикация lineage и результатов dbt-тестов

### `emit_dbt_lineage`

Запускает `src.lineage.emit_dbt` с manifest dbt-проекта. Эмиттер публикует зависимости dbt-моделей через OpenLineage.

### `ingest_dbt_tests`

Запускает OpenMetadata ingestion по двум конфигурациям:

- `dbt/ingestion/dbt_core.yml`;
- `dbt/ingestion/dbt_marts.yml`.

Команды выполняются последовательно в одной Bash-задаче:

```bash
metadata ingest -c dbt/ingestion/dbt_core.yml &&
metadata ingest -c dbt/ingestion/dbt_marts.yml
```

Оператор `&&` запускает ingestion Marts только при успешном завершении ingestion Core. Если первая команда возвращает ненулевой код завершения, вторая не выполняется, а Bash возвращает ошибку задачи.

Ingestion регистрирует в OpenMetadata поддерживаемые тест-кейсы и результаты dbt-тестов. Это публикация метаданных, а не трансформации.

### `push_dbt_test_results`

Запускает `src.lineage.emit_dbt_test_results` с `run_results.json`, сформированным при выполнении тестов dbt.

Скрипт публикует результаты выбранных reconciliation-тестов, которые стандартный dbt-коннектор может пропустить из-за неоднозначных зависимостей `ref` и `source`. Список тестов и таблиц-носителей определяется белым списком `PUSH_CASES`.

Задача запускается после `ingest_dbt_tests`: порядок важен, поскольку ingestion-коннектор должен сначала создать поддерживаемые тест-кейсы, чтобы дополнительная публикация не создавала дубликаты.

Подробности реализации, контракта API и диагностики в [OpenMetadata](../data_quality/openmetadata.md).

## 8. Дата батча, имя источника и повторный запуск

`ds` используется как `batch_date` в загрузке ODS, Python-гейтах и dbt. Для CSV берётся файл соответствующего месяца `--source-file "data/raw/{ds[:7]}.csv"`.

Пример вызова загрузчика для конкретной даты:

```bash
python -m src.ingestion.load_ods \
  --batch-date 2019-10-01 \
  --source-file data/raw/2019-10.csv \
  --load-mode config \
  --resume
```

При повторном запуске того же `batch_date`:

- ODS-загрузчик использует `--resume` и журнал загрузки;
- PySpark повторно обрабатывает партию согласно своей логике;
- инкрементальные dbt-модели используют `batch_date` для фильтрации и, где предусмотрено моделью, удаляют и пересчитывают соответствующие целевые данные.

Повторяемость отдельных этапов не означает атомарности всего DAG. PostgreSQL, ClickHouse, dbt и OpenMetadata не объединены общей транзакцией. Ошибка позднего этапа не откатывает автоматически уже выполненные загрузки и трансформации.

## 9. Повторы, ошибки и статусы

Настройки DAG задают число повторов и задержку между попытками через `_conf`. Для `refresh_dbt_manifest` и группы `process_dbt` повторы явно отключены (`retries=0`).

Следует различать:

1. Ошибка обработки или DQ-gate. Задача завершается с ошибкой; последующие задачи активной цепочки не выполняются.
2. Ошибка ingestion OpenMetadata. Задача `ingest_dbt_tests` может завершиться с ошибкой; `push_dbt_test_results` в этом случае не запускается.
3. Ошибка best-effort эмиттера. Для Python-эмиттеров lineage и публикации DQ предусмотрена обработка ошибок с предупреждением в логе; ошибка отправки может не менять статус основной задачи.
4. Ошибка после записи данных. Ранее выполненные изменения в Core или Marts не откатываются автоматически.

Успешный статус DAG не заменяет анализ DQ-результатов и проверку полноты опубликованных метаданных.

## 10. Одноразовая инициализация

В DAG объявлены задачи, предназначенные для разовой инициализации ODS, индексов и Core:

- `init_ods`;
- `init_ods_indexes`;
- `init_core`.

Вызовы этих задач в активной цепочке отключены. Ежедневный DAG не нуждается в создании этих структур автоматически: первичная инициализация выполняется отдельно.

Важно. `init_ods_indexes` запускается после завершения исторического бэкфилла, а не на каждом ежедневном батче. Этот этап создаёт индексы, возвращает настройки `autovacuum` и обновляет статистику. Повторное создание индексов в ежедневном режиме не требуется и может ухудшить производительность.

Пример отдельного запуска индексации:

```bash
python -m src.db.init_ods --stage indexes
```

## 11. Границы ответственности

| Компонент | Ответственность |
|---|---|
| Airflow | Расписание, зависимости, передача параметров, повторы и статусы |
| ODS loader | Чтение CSV, загрузка в PostgreSQL ODS, возобновление |
| PySpark | Обработка и дедупликация событий, загрузка Core |
| Python DQ-gates | Проверки границ CSV -> ODS и ODS → Core |
| dbt | Измерения, факты, витрины и dbt-тесты |
| OpenLineage | Передача сведений о происхождении данных и зависимостях |
| OpenMetadata | Хранение и отображение каталога, lineage и результатов DQ |

Airflow не отвечает за:

- атомарность изменений между системами;
- корректность бизнес-метрик;
- гарантированное наличие lineage при сбое соответствующих задач.
