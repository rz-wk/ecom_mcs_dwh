# Физическая схема DWH `ecom_mcs_dwh`

## 1. Назначение

Документ описывает физическую организацию хранилища: базы данных и схемы, таблицы, движки хранения, партиционирование, ключи сортировки и индексы.

Смысл полей и их типы описаны в [словаре данных](data_dictionary.md). Назначение слоёв и преобразования данных — в документации [архитектуры](../architecture/architecture.md).

## 2. Состав хранилища

| Система | База / схема | Назначение |
|---|---|---|
| PostgreSQL | `ingestion` | Журнал загрузки исходных файлов |
| PostgreSQL | `ods` | Исходные события с техническими метаданными загрузки |
| ClickHouse | `ecom_mcs_dwh_core` | Очищенные события, измерения и факты |
| ClickHouse | `ecom_mcs_dwh_marts` | Агрегированные аналитические витрины |

## 3. PostgreSQL

### 3.1. `ingestion.journal`

Журнал фиксирует состояние загрузки исходного файла для конкретной даты батча.

- Первичный ключ: (`source_file`, `batch_date`).
- Назначение ключа: идентифицировать загрузку по источнику и дате.
- Хранение: обычная таблица PostgreSQL, без партиционирования.

### 3.2. `ods.events`

ODS хранит события, загруженные из CSV, вместе с техническими атрибутами загрузки.

- Партиционирование: `RANGE` по `event_time`.
- Индексы:

| Индекс | Поля | Назначение |
|---|---|---|
| `idx_events_batch_event_time` | (`_source_file`, `_batch_date`, `event_time`) | Поиск событий по источнику, батчу и времени |
| `idx_events_event_time` | (`event_time`) | Фильтрация по времени события |
| `idx_events_user_id` | (`user_id`) | Поиск событий пользователя |


ODS сохраняет исходные бизнес-поля и дополняет их служебными атрибутами:

- `_ingested_at` — время загрузки;
- `_source_file` — имя исходного файла;
- `_batch_date` — дата батча.

ODS не является аналитической витриной: подготовка данных для аналитического использования выполняется на последующих этапах.

## 4. ClickHouse Core

Все таблицы Core размещены в базе `ecom_mcs_dwh_core`.

### 4.1. Измерения

| Таблица | Движок | Ключ сортировки | Партиционирование |
|---|---|---|---|
| `dim_user` | `MergeTree` | `user_id` | Нет |
| `dim_product` | `MergeTree` | `product_id` | Нет |
| `dim_category` | `MergeTree` | `category_id` | Нет |

Измерения сортируются по идентификатору сущности. Партиционирование для них не задано.

### 4.2. Факты

| Таблица | Движок | Партиционирование | Первичный ключ ClickHouse | Ключ сортировки |
|---|---|---|---|---|
| `fact_events` | `ReplacingMergeTree` | `toYYYYMMDD(event_date)` | (`user_id`, `event_time`) | (`user_id`, `event_time`, `product_id`, `event_type`, `event_id`) |
| `fact_purchases` | `MergeTree` | `event_date` | Отдельно не задан | (`event_date`, `event_id`) |
| `fact_sessions` | `MergeTree` | `toYYYYMM(session_start)` | Отдельно не задан | (`user_id`, `session_start`, `session_id`) |

#### `fact_events`

`ReplacingMergeTree` используется для хранения событий с дедупликацией на уровне механизма слияния частей по ключу сортировки. Но наличие этого движка не означает, что дубли удаляются немедленно при вставке. Основная логика очистки и дедупликации выполняется PySpark-этапом.

Партиционирование по дате события позволяет организовать хранение по дням.

#### `fact_purchases`

Таблица содержит события покупки, выделенные из `fact_events`. Партиционирование и сортировка ориентированы на дату покупки и идентификатор события.

#### `fact_sessions`

Таблица хранит восстановленные сессии. Партиционирование определяется месяцем начала сессии, сортировка — пользователем, временем начала и идентификатором сессии.

## 5. ClickHouse Marts

Все витрины размещены в базе `ecom_mcs_dwh_marts` и используют движок `MergeTree`.

| Таблица | Партиционирование | Ключ сортировки |
|---|---|---|
| `mart_funnel` | `toYYYYMM(event_date)` | (`event_date`, `category_id`, `brand`, `funnel_stage`) |
| `mart_products` | `toYYYYMM(event_date)` | (`event_date`, `product_id`) |
| `mart_sales` | `toYYYYMM(purchase_date)` | (`purchase_date`, `category_id`, `brand`) |
| `mart_sessions` | `toYYYYMM(session_start)` | (`session_start`, `user_id`, `session_id`) |
| `mart_users` | `toYYYYMM(event_date)` | (`event_date`, `user_id`) |

Партиционирование витрин по месяцу уменьшает количество партиций по сравнению с дневным партиционированием событийного Core. Ключи сортировки соответствуют основным измерениям агрегации и типичным фильтрам аналитических запросов.

## 6. Правила сопровождения схемы

При изменении физической схемы проверить:

1. DDL целевой таблицы и конфигурацию модели dbt;
2. ключи сортировки и партиционирование с учётом основных запросов;
3. индексы PostgreSQL и их наличие на партициях;
4. соответствие типов и полей в [словаре данных](data_dictionary.md);
5. тесты качества, проверяющие гранулярность, уникальность и согласованность слоёв.
