# `emit_dbt.py` — звено dbt-моделей

**Файл:** `src/lineage/emit_dbt.py`  
**Таск DAG:** `emit_dbt_lineage`  
**Положение в DAG:** после `process_dbt`.

## Что делает эмиттер

Строит рёбра между таблицами Core и Marts по графу зависимостей dbt.

Эмиттер читает `dbt/target/manifest.json`. Для каждой модели определяет её таблицу как выход, а таблицы моделей и источников из `depends_on` — как входы. Seeds, snapshots и tests пропускаются.

## Почему используется manifest, а не Cosmos

Cosmos отправляет OpenLineage-события со schema-facet, в котором отсутствуют типы полей. В текущей конфигурации OM отвергает такие события с ошибкой `400`.

`manifest.json` содержит граф зависимостей dbt и позволяет строить рёбра без этого дефекта. Подробности механизма — в [architecture.md](../architecture.md).

## Маппинг баз dbt на сервисы OM

Обе базы dbt находятся на одном хосте ClickHouse, но в OM зарегистрированы как отдельные сервисы. Эмиттер использует явный маппинг:

```python
_DB_TO_SERVICE = {
    'ecom_mcs_dwh_core': 'clickhouse_core',
    'ecom_mcs_dwh_marts': 'clickhouse_marts',
}
```

### Особенность dbt-clickhouse

В manifest поле `database` может быть пустым или иметь значение `default`. В таком случае фактическая база определяется по `schema` — это учитывает функция `get_fqn`.

Если модель относится к базе, отсутствующей в маппинге, эмиттер выводит предупреждение и пропускает её.

## Обновление графа

Manifest обновляется при изменении графа моделей. В DAG его пересобирает задача `refresh_dbt_manifest` перед запуском `process_dbt`.

Эта задача является единственным писателем общего файла `dbt/target/manifest.json` в данном процессе. `emit_dbt.py` запускается после `process_dbt` и читает актуальную версию manifest.

Для локальной проверки manifest можно пересобрать вручную:

```bash
cd <dbt_project> && dbt parse
```

## Поведение при отсутствии manifest

Если файл отсутствует, эмиттер записывает сообщение в лог и завершает работу, не прерывая DAG. В штатном рабочем прогоне отсутствие manifest не ожидается, поскольку `refresh_dbt_manifest` выполняется раньше.

## Масштабирование

- Новая модель: ребро появится автоматически после обновления manifest, если модель и её зависимости корректно отражены в dbt-графе.
- Новый source в dbt: зависимость подхватывается из `depends_on`, но сущность таблицы источника должна существовать в OM. Её создаёт ingestion-коннектор соответствующего сервиса.
- Новая база dbt: необходимо добавить сервис OM с include-фильтром схемы и запись в `_DB_TO_SERVICE`. См. [setup.md](../setup.md), шаг 1. Модели из базы, отсутствующей в маппинге, пропускаются с предупреждением в логе.
